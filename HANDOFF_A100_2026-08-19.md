## BUG 1 — the rc=141 that killed the A100 SNP run (root cause + fix)

**Symptom.** 2026-08-18 15:00:15, both `snp_dryrun.log` and `snp_run.log` at
**0 bytes**, exit **141**. Nextflow never started. The heartbeat said "partition
COMPLETE" which was true and misleading — the *SNP run* did nothing.

**Root cause — TWO bugs, and you need both to reproduce it:**

- The reference file `curated_L1v4c_refs.tsv` is **CRLF** (see Bug 2). Every
  `reference_path` carries a trailing `\r`.
- The preflight in the A100 `bin/run_wf_curated_L1.sh` is:

      RMISS=$(awk -F'\t' 'NR>1{print $2}' "$REFS" \
        | while read -r f; do [ -f "$f" ] || echo "$f"; done | head -3)

  `read -r` keeps the `\r` (it is not in IFS), so all 86 paths test as missing.
  The 4th `echo` writes to a pipe `head -3` already closed → **SIGPIPE (141)** →
  `set -o pipefail` propagates it → `set -e` aborts the script **one line before**
  it would have printed "references file points at missing files". The check
  written to report the problem is what silenced it.

**Verified four ways** against a copy of the real script:
`unpatched + CRLF → 141 silent | unpatched + LF → ok | patched + CRLF → ok |
patched + LF → ok`. So the CRLF is the trigger and the `| head` is the amplifier.
Fixing only one leaves a run that still fails (just loudly). **Fix both.**

**The fix** (already uploaded as `fix_and_run_v4c.sh` in `wfsnps-v4c-results/` on
Drive; it is idempotent and confirms the diagnosis before changing anything):

- de-CRLF the refs: `sed -i 's/\r$//' curated_L1v4c_refs.tsv`
- in every preflight loop, drain instead of `head`, and strip CR on read:

      # was:  | while read -r f; do [ -f "$f" ] || echo "$f"; done | head -3)
      # now:  | while read -r f; do f=${f%$'\r'}; [ -f "$f" ] || echo "$f"; done | awk 'NR<=3')

  `awk 'NR<=N'` drains its input, so it cannot SIGPIPE the writer.

This whole class of failure is the project's own rule from the memory file
`crlf-refs-file-kills-snp-run-silently`: **rc=141 + a 0-byte log = SIGPIPE from
`| head` under pipefail, not a failed tool.** Check the log *size* before
believing a run "failed partway".

## BUG 2 — the CRLF is written by the code, and 4 writers are still wrong

It is a real `\r\n` line terminator from the writer, **not** in-field, **not**
Excel. `csv.DictWriter`/`csv.writer` default to `lineterminator="\r\n"`; setting
`newline=""` on `open()` (as the csv docs instruct) then preserves it. Every
prior workstation run was immune only because it reads refs with Python
`csv.DictReader`, whose text-mode `open()` strips `\r\n`→`\n`. The **bash** reader
on the A100 path is the first thing that ever saw the raw `\r`.

`merge_L1_refs_bp.py` writes clean (it passes `lineterminator="\n"`). The
**reference-resolution / staging** code re-introduces it. Fix each by adding
`lineterminator="\n"` to the writer:

| file:line | writes | status |
|---|---|---|
| `a100_v4c_partition/partition_v4c.sh:92-93` | `curated_L1v4c_refs.tsv` | **UNFIXED** — this is the file that caused Bug 1 |
| `build_v4c_panel.py:184-185` | `L1v4c_MERGED_METADATA.tsv` | **UNFIXED** |
| `build_v4c_panel.py:205` | `refined_clusters_reconciled.csv` | **UNFIXED** |
| `build_v4c_panel.py:248-249` | staged A100 `inputs/samplesheet.csv` | **UNFIXED** — bites the A100 path |
| `build_v4c_panel.py:253-254` | staged A100 `inputs/refs.tsv` | **UNFIXED** — bites the A100 path |
| `build_v4c_panel.py:237-238` | `curated_L1v4c_refs.tsv` | already fixed (prior chat) |

**Why this matters for Track B specifically:** when you re-fit and re-partition,
you *regenerate* the refs and the staged bundle. If you fix only the downstream
`sed`, the next partition writes CRLF again. **Fix the writers before you
re-partition**, or you will walk straight back into Bug 1.

One-line fix pattern for the Python writers:

    # csv.DictWriter(fh, fieldnames=..., delimiter="\t")
    # ->
    csv.DictWriter(fh, fieldnames=..., delimiter="\t", lineterminator="\n")
    # and csv.writer(fh) -> csv.writer(fh, lineterminator="\n")

For `partition_v4c.sh:93`, same idea: add `lineterminator="\n"` to the inline
`DictWriter`.

## The A100 code gap — why the A100 script is "underdeveloped" vs the RTX 4070

The workstation script `a100_stage/bin/run_wf_curated_L1.sh` is the mature one
(50+ lines of documented rationale). The A100's `~/v4c_partition/bin/
run_wf_curated_L1.sh` was written from scratch on the box the night of the run
because the v4b staging bundle wasn't present. Feature-by-feature:

| capability | workstation | A100 | consequence if missing |
|---|---|---|---|
| `normalize_reference_headers_bp.py` | yes | **no** | RAxML segfaults on run ids ≥128 chars → Gubbins reports "Unable to fit model to data" → looks like a bad reference. See memory `raxml-128-char-run-id-segfault`. |
| pins `--gubbins_iterations 5 --gubbins_min_snps 3 --gubbins_use_hybrid false` | yes | **no** | Different Gubbins params shift r/m by 0.47–0.78× **non-uniformly** (memory `gubbins-params-shift-rm-nonuniformly`). A100 results would **not be comparable** to workstation/v4b. This is the most important one. |
| pins `--iqtree_support true`, `--max_cluster_size 1000` | yes | **no** | branch supports / cluster cap differ silently |
| `COLLDIR` reference re-resolution by basename | yes | **no** | a reference path that dies with its work dir can't be recovered |
| `RESUME_SESSION=<id>` (resume a *specific* session) | yes | **no** | bare `-resume` can attach to a stray `-preview` session with zero cached tasks and silently re-run everything (memory `nextflow-resume-and-errorstrategy-traps`) |
| `DRY_RUN=1` preflight | yes | yes | — |
| `EXCLUDE_UNITS` / retry-with-alternate-reference | yes | **no** | can't promote a unit to its alternate reference without hand-editing |
| preflight uses `awk 'NR<=N'` not `\| head` | (n/a, Python) | **no — has `\| head`** | Bug 1 |

**Recommendation: do not patch the A100 script — replace it with the workstation
one.** `a100_stage/bin/run_wf_curated_L1.sh` already parameterises everything
machine-specific through env vars (`BASE NFDIR PROFILE COLLDIR OVERRIDES CLUSTERS
REFS ALLSS GENSS OUTDIR WORKDIR RESUME_SESSION`). On the A100 you set:

    PROFILE="bp,dgx_station_a100_updated,docker"
    COLLDIR=<A100 fasta dir>
    OVERRIDES=<A100 overrides>   # a100_stage/curated_L1_overrides_a100.config exists
    # BASE/NFDIR/OUTDIR/WORKDIR to the A100 locations

and it runs with all the guards above. The A100 profile
(`dgx_station_a100_updated`) already exists in `nextflow.config`; keep using it.
This makes the A100 a first-class runner instead of a fork that drifts.

## The scientific reason for the trip — fit quality (Q5)

v4c reused the workstation PopPUNK fit rather than re-fitting. Coverage actually
went **up** (79.0% vs v4b 77.7%), so this is not a coverage regression — it is a
**partition-balance** problem. Unit counts, v4b → v4c:

    strain_1   17 → 26  (+9, expected: fastbaps subdivides the big strain finer)
    strain_4   14 →  4  (-10  <-- the real problem)
    strain_6    6 →  2  (-4)
    total      95 → 86

Fewer, larger units are worse for Gubbins (recombination inferred across lumped
sub-populations inflates r/m — the exact failure mode documented in
`rm-spread-is-divergent-members` and the all35 run). strain_4 collapsing to 4
units is the signature of a coarse strain boundary upstream.

**The experiment:** on the A100, re-fit PopPUNK from scratch (it has the memory
that forced the reuse in the first place), re-run PopPIPE/fastbaps, re-partition.
Hypothesis: a fresh fit rebalances strain_1/strain_4 and yields a v4b-like unit
count without losing the coverage gain.

**This is a hypothesis, not a certainty** — verify it, don't assume it:
- compare the new per-strain unit table against the one above;
- confirm strain_4 recovers toward ~14 and strain_1 doesn't explode;
- keep Track A's partition as the control so you can tell whether the re-fit
  actually helped or just moved the boundaries around.

Relevant memory: `min-cluster-size-applied-twice`, `l1v4b-partition-is-the-
current-result`, `fastbaps-needs-a-rooted-tree-or-it-returns-all-ones` (a re-fit
regenerates guide trees — make sure they're rooted or fastbaps writes all-1s).

## The ska strain_1 OOM — context, and whether it still matters

On the workstation, `ska build` on the 901-genome strain_1 needed ~500–600 GB and
OOM-killed the box; on the A100 the monolithic build climbed past 456 GB before
being killed too. It was solved by building in **8 batches of 113** (~13–14 GB
peak each) then `ska merge` — equivalence verified (identical column multisets).
That workaround is in `strain1_build.log` / the A100 orchestrator.

**If the re-fit gives a smaller largest strain** (workstation caps monolithic ska
at ~650 genomes; memory `skabuild-ooms-on-large-strains-workstation`), the batched
build may be unnecessary. If strain_1 is still ~900, keep the batching. Either
way, the merged dictionary is only ~2 GB — the memory blowup is purely the
`n_samples`-wide per-kmer vector in every thread, not the output.

## The ONT base-accuracy check (Q2) — do this before trusting two genomes

`SRR28096039` (gene-count ratio **1.08**) and `SRR28096043` (**1.06**) are the two
**highest** ratios in the entire 171-genome passing batch (median 0.97, p90 0.99).
They are **Oxford Nanopore** (2 contigs, N50 ~4 Mb, 100% core) — which is why
there is no SPAdes swap and no override-register entry: nothing to swap. But a
gene-count ratio just above 1 is the residual-indel / frameshift signature, and
2-contig contiguity **hides** it — the same trap as the PacBio CLR Ceará
assemblies (`pacbio-clr-failure-is-base-accuracy`). They pass the ≤1.20 gate
(calibrated on 1.35+ CLR failures), so they were not screened beyond that.

**Check before trusting them:** BUSCO complete-vs-fragmented, or read-level QV /
Medaka-style consensus polishing evidence. If they're clean, keep them; if
fragmented-gene-heavy, they're indel-noisy and should be flagged or dropped.
`additions/fasta_new200/` is a **batch** label ("new200"), not an assembler label
— it holds both SKESA Illumina and these two ONT.

## Verification discipline (the standing rules — apply to every number)

- **errorStrategy is 'ignore':** a zero exit ≠ every unit succeeded. Run
  `collect_L1_results.sh`, read `Summaries/cluster_phylogeny_summary.csv`, count
  units that actually produced Gubbins output vs units requested. (memory
  `nextflow-resume-and-errorstrategy-traps`)
- **Partial-denominator error:** never compute a percentage against "seen so far".
  Six appendix figures were once wrong this way. (memory `partial-denominator-error`)
- **Check per-item values, never infer from a summary line.** Every defect in this
  project produced plausible output from a silent mismatch, caught only by
  comparing raw values against what they should have been.
- **rc=141 + 0-byte log = SIGPIPE in the shell, not a tool failure.** (Bug 1)
